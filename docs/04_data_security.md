# 04 数据与安全

## 1. v0.1数据边界

M0/M1 不引入数据库；进入持久化阶段后新建 SQLite 存储适配器与数据库，由宿主集中写入，不让每个房间直接打开共同账号文件。数据库位于配置指定的可写持久目录，不写死开发机盘符或打进只读资源包。上线前评估实际并发与备份需要，再决定是否迁移 PostgreSQL。

设计 Repository 接口，但不要为了未来切换实现先支持两种数据库。

建议实体：users、sessions、games、builds、rooms、reservations/memberships、matches、result_events、schema_migrations。活跃进程和心跳不是重启后可以直接信任的历史记录；需要与实际进程核对。

游戏专有数据按 game_id 隔离，采用项目自己的表或带 schema_version 的受校验文档，不在通用用户表里硬编码 guns 或任何具体玩法字段。数据库迁移脚本与备份恢复测试需版本管理。

## 2. 身份与授权

开发游客身份只用于本地/受控测试，不能据此宣称完成正式账号安全。AuthProvider 保留接入已有账号系统的边界，第一版不自制完整密码找回、邮件和支付体系。

本项目没有需要迁移的旧密码库。正式实现密码登录时，口令应采用成熟实现的专用密码哈希；OWASP优先推荐Argon2id，不使用明文、可逆加密或普通SHA-256替代密码哈希。[S8] 也可接入成熟身份提供方，避免自行实现密码系统。

账号会话、短时入房票据、房间控制凭据是三种不同凭据，不能混用。票据过期/核销由可信服务端判定，客户端时钟不作为依据。

## 3. 信任边界

不信任客户端的user_id、阵营、分数、金币、角色位置和命中声明。user_id来自会话；对局输入由实际玩法进行权限、频率、状态和范围校验。

控制接口仅回环监听，并使用每次启动独立的房间凭据。仅有room_id或连到127.0.0.1不足以证明身份。凭据通过权限受限的文件/受控通道交付，不放在日志或明文命令行参数中。

此设计默认宿主运行管理员信任的游戏构建。不同进程不等于安全沙箱；允许不可信第三方代码或模组上服需要另外设计OS/容器隔离、文件系统权限与网络访问限制。

## 4. 网络与资源防护

公网大厅要求WSS及证书验证，按连接、身份、IP等适当限流，限制消息长度、队列和连接数。WebSocket的认证、授权、大小限制与敏感日志处理需要独立检查。[S9]

公网房间不发送账号密码。鉴权不能替代传输加密；DTLS证书、密钥部署和被动抓包检查必须通过正式发布门禁。[S5]

未认证客户端不生成游戏实体，不接收游戏RPC；开启认证中连接上限与短超时。不得允许任意对象反序列化。Godot 文档警告 allow_object_decoding 对不可信对象可能导致代码执行，保持关闭。[S3]

限制每用户可创建房间数、全宿主房间/人数上限和每游戏配额；限制排队请求。容量不足返回明确错误，不无限启动进程。

## 5. 结算幂等与落盘

房间提交 game_id、build_id、room_id、launch_id、match_id、result_id、result_kind、结果版本和受校验payload。宿主验证房间身份及所属关系，再持久化。

同一result_id重试返回相同确认；同一ID不同payload返回冲突。最终结果还应对(game_id, match_id, result_kind)设置唯一约束，防止换一个result_id重复发奖。写入与必要的业务处理应有明确事务/事件边界。

宿主持久化成功后才ACK。房间未收到ACK可重试，超时则先写入持久化outbox再退出，恢复后幂等重发。不能把结果只存在内存后直接退出，也不能承诺灾难后绝不丢失，需说明存储和备份保证。

结果须区分completed与aborted，崩溃或控制失联中止不能伪造正常胜负。核心可以接收并去重结果，但不能自动理解每个游戏的金币和排行榜规则。项目奖励处理单独实现，也需要幂等。
