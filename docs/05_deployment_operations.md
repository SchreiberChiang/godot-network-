# 05 部署、运维与发布

## 1. v0.1部署形态

按 Windows 本地开发、Linux 原生单机部署设计两个 ProcessLauncher 适配器；具体支持的系统/架构以实际测试为准。不要求第一版使用Docker、Kubernetes或多机调度。M0/M1 先验收当前开发平台；未运行 Linux 测试不得声称 Linux 已支持。

启动真实导出的服务端二进制，不通过可被用户拼接的cmd/bash字符串执行。OS.create_process 支持启动独立进程；游戏自定义参数应置于 `--` 后，由 OS.get_cmdline_user_args 读取。[S10]

设计示意（文件与程序尚未实现）：

```sh
./shooter_server --headless -- --launch-config=/srv/roomhost/run/launch_001/config.json
```

路径只是示例。启动配置/凭据文件应有适当权限；公开命令行不直接携带秘密。导出客户端与专用服务器是独立产物，Godot支持专用服务器资源剥离与命令行导出。[S1][S11]

## 2. 目录建议

`releases/<game_id>/<build_id>/`：不可变游戏产物。

`config/`：宿主与游戏注册清单；秘密单独保管。

`data/`：数据库、结算outbox和持久启动记录。

`run/<launch_id>/`：本次实例工作目录与非持久临时数据。

`logs/`：按游戏/实例识别，配置轮转，不把全部日志积累在根目录。

outbox不得随临时run目录清理而丢失。

## 3. 端口与地址

游戏端口范围示例为UDP 10000–10199，本机房间控制端口示例为TCP9999，但只绑定回环。端口均为建议值，需配置而非写死。WSS可由经过配置的TLS入口终结后转发到本机标准WebSocket。

绑定地址与对外advertise地址分开，不能把0.0.0.0或127.0.0.1回给外网客户端。防火墙与路由需与游戏UDP范围一致；WSS入口不会自动代理游戏UDP。

分配端口与启动要在宿主中串行/加锁；测试“先检查空闲后被占用”的竞态。最终以子服实际绑定和ready为准。关闭时确认进程身份及终止后再释放租约。

## 4. 日志与监控

日志字段：timestamp、level、event、game_id、build_id、room_id、launch_id、request_id，以及不泄密的错误码。不得记录完整会话令牌、票据或密码。

至少观察：开房成功率、启动耗时、活跃/异常实例、CPU/内存、单房模拟步耗时及P95/P99、收发带宽、认证失败、心跳滞后、结果积压、端口使用、可用磁盘。

日志要区分：进程启动失败、端口绑定失败、地图加载失败、认证失败、版本不符、控制连接失败。不要全部记为“网络异常”。

## 5. 重启与更新

正常更新：新房使用新build；旧房drain，不再分配新成员；按策略让进行中对局结束；确认结果和进程退出后移除旧产物。不原地覆盖正在运行的构建，不强迫旧客户端进入新不兼容房间。

v0.1不承诺主服重启无感：宿主恢复先隔离并核对遗留实例；旧房失联后在宽限内退出或受控中止。不得把PID复用误认为原实例，也不得对未知进程直接kill。

单机断电/断网仍是整体故障。进程隔离不是高可用。

## 6. 自动化交付目标

计划提供（尚未实现）：Windows本地启动脚本、Linux启动脚本、构建/导出脚本、清单验证脚本、部署与回滚脚本、日志检查脚本。

CI应固定Godot精确版本和导出模板，检查配置/schema、运行headless测试、导出双端、运行最小联机/进程生命周期测试。新增脚本后必须把真实命令和期望输出补进QUICKSTART，不能保留只有名字的“一键脚本”。

发布前实际执行一次数据库备份恢复和一次旧构建回滚。
